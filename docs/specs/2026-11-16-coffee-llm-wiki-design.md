## 1. 意圖與目的

作業要求：先用「先討論、後生成」的方式建立一個自選主題的 LLM Wiki（至少 ingest 5 篇資料），再把 Wiki 當成知識來源，產生一份教學型 HTML 簡報，並說明 loop／graph 設計、附上實際執行紀錄與反思。

Wiki 架構參考 Karpathy 的〈LLM Wiki〉構想：raw sources（不可改）→ wiki（LLM 維護、互相連結的 markdown）→ schema（`CLAUDE.md`，規定 wiki 結構與流程）。三個操作是 ingest、query、lint，並用 `index.md`（目錄）與 `log.md`（時間序紀錄）輔助。

**主題：咖啡入門。**

**簡報的學習目標（使用者決定）：** 看完的人走進精品咖啡店，看得懂菜單和豆子標籤，知道怎麼點到自己會喜歡的咖啡。觀眾是原本不懂咖啡的人。

評分最高級（9–10 分）要求：Wiki 與簡報有明確對應、graph 設計合理且說明清楚、有實際執行與檢查紀錄、反思哪個節點容易出錯並如何提前檢查、簡報有清楚教學結構。

## 2. 目標、非目標、反目標

**目標**
- Wiki：至少 5 篇（目標 6–7 篇）來源 ingest 完成，概念頁互相連結，`index.md`、`log.md` 完整。
- 簡報：可直接在瀏覽器開啟翻頁的單一 HTML，教學結構清楚，每頁標註引用的 Wiki 頁面。
- 報告：涵蓋作業要求的 6 項繳交內容。
- 整個資料夾放上 GitHub，Wiki 可在 GitHub 網頁瀏覽，簡報透過 GitHub Pages 有公開網址。

**非目標**
- 不教怎麼在家手沖或操作義式機（沖煮只講到「菜單上看到時知道差別」）。
- 不寫可重跑的程式化 pipeline（不使用 LangGraph／API key）。
- 不追求學術論文來源。

**反目標（就算做完也算失敗）**
- 簡報出現 Wiki 裡沒有的事實（Wiki 和簡報對不上）。
- 執行紀錄或反思是編造的：反思必須根據 `log.md` 的實際紀錄來寫，不能事先寫好。
- 把受版權保護的文章全文或圖片公開放上 GitHub。
- 簡報對初學者太硬，術語沒有解釋。

## 4. 考慮過的做法（Approaches）

**Graph 執行方式**
- **A. Claude Code 照 `CLAUDE.md` 規則執行（採用）**：節點和檢查關卡寫進 schema，逐步執行，每個節點結果寫進 `log.md`。不需要 API key，最貼近 Karpathy 範本，人工檢查點容易插入。代價是 graph 是「規則＋紀錄」而不是能重跑的程式。
- B. Python／LangGraph 程式：graph 是具體程式碼，但需要 API key、有費用、開發時間長，人工檢查點要中斷程式等待輸入。

**簡報技術**
- **A. 手寫單一 HTML（採用）**：無外部依賴，方向鍵翻頁，圖用 SVG/CSS 畫，視覺彈性最大。使用者選咖啡就是看重視覺。
- B. reveal.js：翻頁功能完整，但版面受框架限制。
- C. Marp：跟 markdown 對應最直接，但視覺最陽春。

**Ingest 參與程度**
- 逐篇討論（最符合 Karpathy，但耗時）vs. 一次批次確認（省時，但討論痕跡少）。
- **採用折衷：三個人工檢查點**（見第 6 節）。

## 5. 已決定的設計

### 5.1 資料夾結構

```
tenth week/
├── CLAUDE.md                 ← schema：頁面格式、各節點流程與檢查規則
├── README.md                 ← repo 首頁：作業說明＋Wiki／簡報／報告連結
├── .gitignore                ← 排除 raw/ 下的全文
├── raw/
│   ├── SOURCES.md            ← 公開：來源清單（標題、網址、日期、用途）
│   └── *.md                  ← 不公開：擷取的全文
├── wiki/
│   ├── index.md              ← 目錄，依類別列出所有頁面＋一行摘要
│   ├── log.md                ← append-only，格式 `## [YYYY-MM-DD] <操作> | <標題>`
│   ├── overview.md           ← 咖啡入門總覽
│   ├── sources/              ← 每篇來源一頁摘要
│   ├── concepts/             ← 概念頁
│   └── outputs/              ← query 產物存回 wiki（例如簡報大綱）
├── slides/
│   └── index.html            ← 教學簡報
├── report.md                 ← 繳交文件（6 項內容）
└── docs/specs/               ← 本設計文件
```

### 5.2 Wiki 頁面慣例
- 連結一律用標準 markdown 相對路徑 `[拿鐵](../concepts/latte.md)`，不用 `[[ ]]`，這樣在 Obsidian graph view 和 GitHub 網頁上都能點。
- 每頁有 YAML frontmatter：`title`、`type`（source／concept／overview／output）、`sources`（引用的來源頁清單）、`updated`。
- 概念頁的每個事實陳述要能追到至少一個來源頁（行內標註，如 `（來源：[SCA 風味輪](../sources/sca-flavor-wheel.md)）`）。
- 來源之間有矛盾時，在概念頁明確寫出「A 說…，B 說…」，不要自行選邊。

### 5.3 內容範圍與比重（依學習目標）

| 區塊 | 比重 | 要回答的問題 |
|---|---|---|
| 菜單上的飲品 | 重 | 濃縮、美式、拿鐵、卡布奇諾、馥列白、瑪奇朵等差在哪（濃縮、奶、奶泡的比例） |
| 豆子標籤怎麼讀 | 重 | 產區、海拔、處理法（水洗／日曬／蜜處理）、品種、烘焙日期、風味描述 |
| 烘焙度 | 中 | 淺／中／深焙的風味差異 |
| 風味輪 | 中 | 「莓果、柑橘、焦糖」這類描述是什麼意思、為什麼不是加香料 |
| 沖煮方式 | 輕 | 手沖、義式、冷萃在菜單上的差別 |
| 點餐決策（收尾） | — | 喜歡酸還是苦、加不加奶 → 推薦點法 |

概念頁的最終清單依實際來源決定（builder 自行判斷）。

### 5.4 Loop／Graph 設計

```
[N1 找候選來源] ──▶ ◆檢查點1：使用者選 ≥5 篇
        ▲                        │
        │                        ▼
        │              [N2 擷取到 raw/] ──▶ 檢查：內容完整？（不是付費牆、不是空白頁）
        │                        │                      └─ 不通過 → 換來源，回 N1
        │                        ▼
        │        ┌─▶ [N3 Ingest 一篇]：讀 → 列重點 → 寫 source 頁 → 更新 concept 頁 → 更新 index → 寫 log
        │        │               │      檢查：每個事實都標了來源？
        │        │               │      ◆檢查點2：第 1 篇完成後使用者確認格式／深度／用詞（校準範本）
        │        └── 下一篇 ◀────┘  （每篇來源跑一次 loop）
        │                        ▼
        └── 補資料 ◀── [N4 Lint]：矛盾、孤兒頁、缺頁、沒標來源的陳述、未涵蓋的學習目標
                                 ◆檢查點3：使用者決定補資料／標註矛盾／忽略
                                 ▼
                     [N5 Query]：讀 index → 依學習目標找相關頁面
                                 ▼
               ┌──▶ [N6 簡報大綱]：逐頁列出重點＋引用的 wiki 頁
               │                 檢查：每頁都有 wiki 引用？術語有解釋？涵蓋學習目標？
               └── 重寫 ◀── 不通過
                                 │  ◆使用者確認大綱 → 大綱存成 wiki/outputs/slide-outline.md
                                 ▼
               ┌──▶ [N7 生成 HTML]
               │                 檢查 a：逐頁事實核對（簡報陳述 vs. 引用的 wiki 頁）
               │                 檢查 b：瀏覽器實際打開（翻頁、版面、手機寬度、無錯誤）
               └── 重新生成該頁 ◀── 不通過
                                 ▼
                     [N8 寫報告]：graph 說明、執行紀錄摘錄、反思
```

**會重複執行的**：N3（每篇來源一次）、N4→N1/N3（lint 找到缺口時補資料）、N6（大綱檢查不過時重寫）、N7（某頁事實核對或渲染不過時，只重新生成該頁）。

**為什麼這樣設計**：錯誤越晚發現，修正成本越高。所以每個生成節點後面都接一個檢查，而且是「可追溯的引用」這種能機械式判斷的檢查。人工檢查點放在三個成本槓桿最大的地方：選來源（垃圾進垃圾出）、第一篇 ingest（後面照它的格式跑）、lint 結果（決定 wiki 夠不夠支撐簡報）。

**紀錄**：每個節點執行和每次檢查（通過或失敗、失敗原因、怎麼修）都寫進 `log.md`。三個檢查點的討論內容和使用者決定也要記錄。

**反思的寫法**：實際跑完後，從 `log.md` 統計哪個節點失敗最多、把檢查往前移到哪一步、有沒有因此修改 `CLAUDE.md` 或 graph。如果執行中修改了 graph，`CLAUDE.md` 和報告都要記錄修改前後的差異與原因。

### 5.5 簡報
- 單一 `slides/index.html`，不依賴外部套件（可用 Google Fonts）。
- 方向鍵／點擊翻頁，顯示頁碼，手機寬度可讀。
- 長度約 15–20 頁，教學結構：開場（為什麼看不懂菜單）→ 菜單飲品 → 豆子標籤 → 烘焙度 → 風味輪 → 沖煮方式 → 點餐決策樹 → 總結。
- 每頁底部標註引用的 Wiki 頁面（可點連到 GitHub 上的該頁）。
- 圖用 SVG/CSS 自繪：飲品組成剖面圖、烘焙色階、簡化版風味輪、標籤拆解圖、決策樹。

### 5.6 報告（`report.md`）
對應作業 6 項：
1. Wiki 主題與簡介
2. Wiki 連結（GitHub repo）＋ Obsidian graph view 截圖（若使用者能提供）

## 6. 人工檢查點（使用者決定的參與程度）

1. **選資料**：提出 6–7 篇候選，每篇附一行「它補哪一塊」，使用者選出至少 5 篇或要求更換。
2. **第一篇 ingest 後**：使用者確認格式、深度、用詞；之後幾篇照這個標準批次進行，不再逐篇停下。
3. **Lint 後**：使用者決定怎麼處理矛盾、缺頁、孤兒頁。

另外，簡報**大綱**生成後也要使用者確認，再生成 HTML。

## 6.5 審查後補充的決定（我的決定，使用者可改）

- **raw/ 的擷取方式**：用網頁擷取工具抓取，存成 markdown，開頭記錄網址、擷取日期、擷取方式。N2 檢查「內容完整」的標準：正文至少涵蓋該來源被選用的那一塊、不是付費牆或錯誤頁。被擋或內容不全的來源直接換掉（回 N1），不要求使用者手動存檔；但使用者也可以用 Obsidian Web Clipper 手動補。
- **今天的設計討論算「先討論」階段**：`log.md` 第一筆是 `## [2026-11-16] discuss | 需求與設計討論`，如實摘要這次對話的決定（主題、學習目標、內容比重、參與程度、做法 A＋A），並註明「依當日對話整理」。這是真實發生的紀錄，不是編造。
- **點餐決策樹屬於綜合整理（synthesis）**：存成 `wiki/outputs/ordering-guide.md`，frontmatter 的 `type: synthesis`。每個分支背後的事實（例如「淺焙酸度較明顯」）都要引用 concept 頁；建議本身標註為「根據以上整理的建議」。Lint 和 N7 的事實核對接受這類頁面，前提是其底層事實都有引用。

- **繳交形式（使用者未指定，採預設）**：`report.md` 放在 GitHub repo，繳交時貼上 repo、簡報、報告三個連結。流程圖用 mermaid，GitHub 會直接渲染。最後一步保留「視需要匯出 PDF」，若課程平台要求上傳檔案再做。GitHub 推送排在簡報完成後、11/22 以前，保留一天緩衝。
